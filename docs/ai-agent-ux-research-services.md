# 메일을 넘어 109개 서비스로: AI 에이전트 UX/UI 연구 정리 (2편)

> 1편: [메일 앱보다 편한 AI 에이전트](ai-agent-ux-research.md) — 메일 과부하, 혼합 주도, 신뢰 연구.
> 이 문서: 같은 원칙을 [한국 주요 서비스 109개](korea-top100-services.md)(쇼핑·예약·SNS·OTT·공공 등)로 넓힐 때
> 무엇이 달라지는지, **웹/GUI 에이전트** 연구(CHI 2025–2026 중심)와 **한국 법규**를 더해 정리했습니다.

---

## 0. 한 줄 결론

**서비스 109개를 109가지 화면으로 만들지 말고, "행동 유형" 6가지로 묶어 같은 UI 부품으로 처리한다.**
메일에서 얻은 원칙(먼저 정리해 보여 주기 · 묶어서 승인 · 되돌리기)은 그대로 쓰되, 웹 서비스에는 세 가지가 더 필요합니다.

1. **실행 중에 끼어들 수 있게** — 웹 에이전트는 메일 API보다 훨씬 자주 틀립니다. 사람이 15%만 거들면 성공률이 95%까지 오릅니다 (CowPilot).
2. **승인은 "정확한 내용"에 묶기** — "결제해도 돼?"가 아니라 "이 상품·이 옵션·이 금액·이 판매자"를 승인. 내용이 바뀌면 다시 승인 (AP2 Cart Mandate).
3. **사이트가 에이전트를 속이는 것까지 막기** — 다크패턴, 광고·상단 노출 편향, 개인정보 입력 유도는 사람보다 에이전트가 더 잘 속습니다 (CHI 2026).

## 1. 메일과 웹 서비스는 무엇이 다른가

| | 메일 (Gmail API) | 웹 서비스 (브라우저 조작) |
| --- | --- | --- |
| 조작 방식 | 정해진 API, 결과가 예측 가능 | 화면을 읽고 클릭, 사이트 개편·팝업·로딩에 취약 |
| 틀렸을 때 | 휴지통에서 복구 가능 | 주문·예약·게시는 **되돌리기 어렵거나 비용 발생** (취소 수수료) |
| 상대방 | 나 혼자 (전송만 예외) | 판매자·다른 사용자·공공기관 — **다른 사람에게 영향** |
| 속임수 | 메일 속 프롬프트 인젝션 | + 다크패턴, 광고 배치, 가짜 긴급성("3개 남음") |
| 개인정보 | 메일 내용 | + 주소·전화번호·결제수단·신분 정보를 **폼에 입력** |
| 사람만 할 수 있는 구간 | 거의 없음 | 로그인, 본인인증(PASS·간편인증), 결제 비밀번호, 캡차 |

그래서 메일 문서의 원칙에 **실행 중 개입 · 내용 고정 승인 · 사이트 불신**이 더해져야 합니다.

## 2. 새로 추가된 연구 근거 (웹·GUI 에이전트, 2025–2026)

### 2.1 사람이 조금만 거들면 훨씬 잘 된다
| 연구 | 발견 | 설계 |
| --- | --- | --- |
| **CowPilot** (Huq et al., NAACL 2025 Demo) — 쇼핑·SNS 등 실제 사이트 | 에이전트가 다음 행동을 제안하고 사람은 멈춤·거절·직접 조작. **협업 모드 성공률 95%**, 완전 자동보다 47%p 높음. 사람이 한 단계는 **전체의 15.2%**뿐 | "완전 자동" 대신 **언제든 멈추고 넘겨받는** 실행 화면 |
| **"Here, Let Me Help"** (Kim, …, Ko, **CHI 2026**) — 30명, 쇼핑·여행·정보 탐색 12개 과제, 실제 사이트 | 사용자 개입은 **명시적**(멈춤·덮어쓰기)과 **암묵적**(미리 필터 걸어 두기·화면 준비)으로 나뉨. 개입 이유는 주로 **오류 수정**과 **선호 불일치**(지시가 불충분) | 개입 버튼 외에 **"조건 추가"**(예산·브랜드·날짜)를 실행 중에도 넣을 수 있게 |
| **Modeling Distinct Human Interaction in Web Agents** (2026, 400개 실제 궤적) | 사용자 유형 4가지: 손 떼고 감독 / 적극 감독 / 함께 풀기 / 완전히 넘겨받기 | 한 가지 UI가 모두에게 맞지 않음 → **감독 강도 선택** |
| **Cocoa** (Feng et al., **CHI 2026**) | 채팅 대신 **공유된 계획 문서**(단계·담당·진행)로 함께 계획·실행하면 조종 가능성↑, 사용 난이도는 그대로 | 긴 작업(여행 준비 등)은 **단계 체크리스트**로 보여 주고 단계마다 "내가 할게 / 네가 해" |

### 2.2 무엇이 불편하고 무엇이 무서운가
| 연구 | 발견 | 설계 |
| --- | --- | --- |
| **Mapping the Design Space of UX for Computer Use Agents** (Apple, **IUI 2026**) — 오즈의 마법사 실험 20명 | ① 에이전트가 **어디까지 볼 수 있고 무엇을 할 수 있는지** 알려야 함 ② 구매·실제 사람과의 상호작용 **전에** 반드시 사용자를 끌어들여야 함 ③ 모호·불확실할 때 사용자가 끼어들 수 있어야 함 | 작업 시작 카드에 **"접근 범위: 쿠팡 계정 · 주문 내역 읽기 · 장바구니 담기"** 표시 |
| **Why Johnny Can't Use Agents** (CMU, 2025; Operator·Manus, 31명) | 5대 장벽: 정신 모델 불일치 · **성급한 신뢰 가정** · 협업 방식 불일치 · **말이 너무 많음** · 스스로 모르는 걸 모름 | 진행 로그는 짧게, **질문은 모아서 한 번에**, "확실하지 않음"을 스스로 말하게 |
| **Characterizing Unintended Consequences of GUI Agents** (**CHI 2026**; SNS 글 221개 + 인터뷰 21명) | 의도를 화면 요소로 옮기는 실패, 화면 변화 대응 실패, **잘못된 실행** → 작업 포기·보안 위험. 사용자는 임시방편(별도 계정·지켜보기)으로 버팀 | 실행 결과를 **검증하는 단계**(주문 후 주문내역 다시 읽어 확인)를 기본으로 |
| **Plan-Then-Execute** (CHI 2025, 1편 참고) | 그럴듯한 나쁜 계획을 믿어 버림 | 계획 단계에 **위험 표시**(💳 결제, 👥 타인에게 보임, ⏱ 취소 수수료) |

### 2.3 사이트가 에이전트를 속인다
| 연구 | 발견 | 설계 |
| --- | --- | --- |
| **Dark Patterns Meet GUI Agents** (**CHI 2026**; 다크패턴 16종, Operator·Claude Computer Use 등 6개 에이전트) | 에이전트는 다크패턴에 **매우 취약** — 알아채지 못하거나, 알아채도 과제 완료를 우선함. 사람 감독이 있으면 나아지지만 **주의 협소·인지 부하·제어 부족**으로 여전히 당함 | 승인 카드에 **사전 체크된 옵션·추가 요금·정기결제 전환**을 자동 강조. 사람이 "찾아내게" 두지 말 것 |
| **What Is Your AI Agent Buying?** (Allouah et al., **WWW 2026**) | 에이전트는 **첫 줄·특정 위치를 강하게 선호**, 모델마다 가격·평점 민감도가 제각각. 판매자가 설명을 살짝 바꾸는 것만으로 점유율이 크게 변함 | 추천 1개만 보여 주지 말고 **비교표(3개 안팎) + 고른 이유**. "광고" 표시 상품은 따로 표시 |
| **When Agents Shop for You** (2026) | 판매자 측 AI가 대화만으로 구매 에이전트의 **지불 의사 금액을 거의 그대로 알아냄** | 에이전트에게 **예산 상한을 사이트에 말하지 않도록** 규칙화 |
| **EchoLeak** (2025, 1편 참고) | 콘텐츠 속 숨은 지시로 데이터 유출 | 상품 설명·리뷰·게시글도 **데이터일 뿐 지시가 아님** |

### 2.4 개인정보와 기억
| 연구 | 발견 | 설계 |
| --- | --- | --- |
| **PrivWeb** (**CHI 2026**; 형성 연구 15명, 평가 14명) | 사용자는 에이전트의 데이터 처리 방식을 **자주 오해**. 민감도에 따라 **낮으면 조용한 알림, 높으면 반드시 멈춤**으로 나눈 방식이 투명성만 제공하는 방식보다 신뢰·보호감↑ | 주소·전화번호 입력은 알림만, **주민번호·계좌·건강 정보는 반드시 멈추고 확인** |
| **ChatGPT 메모리 인식 연구** ("Relational Gains, Privacy Strains", **CHI 2026**) | AI가 무엇을 기억하는지 알게 되면 **대부분 부정적 기대 위반**. 기억을 보고·지우고·고칠 수 있어야 함 | "에이전트가 기억하는 것" 화면: 선호 브랜드·주소·사이즈를 **목록으로 보고 지우기** |

### 2.5 나 대신 말하기 (SNS·커뮤니티·중고거래 채팅·채용 지원)
| 연구 | 발견 | 설계 |
| --- | --- | --- |
| Jakesch et al., **CHI 2019** "AI-Mediated Communication" | AI가 썼다고 **의심되면** 신뢰도가 떨어짐 (Replicant effect) | 게시·댓글·DM은 **초안까지만**, 사용자가 직접 다듬고 올리게 |
| Hancock, Naaman & Levy, *JCMC* 2020 | AI가 대인 커뮤니케이션을 수정·생성하면 관계와 책임 문제가 생김 | 남에게 보이는 모든 행동은 **"누가 보게 되는지"** 를 승인 카드에 표시 |

### 2.6 결제 표준: 승인을 "내용"에 묶기
- **Google Agent Payments Protocol (AP2, 2025)** — 사람이 있을 때의 구매를 3단계 위임장으로 처리:
  **Intent Mandate**("흰색 러닝화 찾아줘") → **Cart Mandate**(사용자가 *정확한 상품·가격*의 장바구니에 서명, 변경 불가) → **Payment Mandate**.
  → 이 앱에 적용하면: 승인은 "10분 안에 아무 결제 버튼 1회"가 아니라 **"승인한 장바구니 내용 = 결제 직전 화면 내용"일 때만 유효**.

## 3. 109개 서비스를 6가지 행동 유형으로

| 유형 | 해당 서비스 (예) | 사용자가 원하는 것 | 기본 자율성 | 사람이 반드시 하는 지점 |
| --- | --- | --- | --- | --- |
| **A. 모아 보기** | YouTube·OTT 5종·음악 4종·웹툰 3종·밴드·카페·블로그·치지직·SOOP·에브리타임 | 새 회차·신작·새 글을 **앱을 안 열고** 알기 | L4 (자동 확인 → 브리핑) | 없음 (읽기만) |
| **B. 비교·구매** | 쿠팡·11번가·G마켓·옥션·네이버쇼핑·롯데ON·SSG·컬리·다이소·올리브영·무신사·알리·테무·도서 3종·오늘의집 | 최저가·조건 맞는 상품을 **골라 장바구니까지** | L3 (비교·담기까지) | **결제** (결제 비밀번호는 handoff) |
| **C. 예약·예매** | 네이버 예약·캐치테이블·CGV·메가박스·롯데시네마·NOL 티켓·코레일·SRT·고속버스·항공 4종·숙박 5종 | 조건 맞는 시간·좌석 찾기 + **선점** | L3 | **예약/예매 확정·결제**, 취소 수수료 확인 |
| **D. 나 대신 말하기** | 인스타·X·페이스북·스레드·밴드·카페 글쓰기·번개장터 채팅·사람인·잡코리아·알바 2종·메일 3종·디스코드 | 초안·답장·지원서를 **내 말투로** | L2–L3 (초안까지) | **게시·전송·지원서 제출** |
| **E. 지켜보기** | 부동산 4종·채용 공고·가격 변동·네이버페이 배송 조회·공공 조회 | 조건이 맞으면 **알려 주기** | L4–L5 (조회는 자동) | 없음 → 행동이 필요하면 B/C/D로 넘어감 |
| **F. 사람 전용 구간** | 정부24·홈택스·건강보험(본인인증), 결제 비밀번호, 캡차 / 금융·PASS·신분증(⛔) / 배민·카카오T 등 앱 전용(❌) | 에이전트가 **거기까지 준비해 두기** | 준비까지만 | 인증·송금·앱 전용 주문은 사용자가 |

> 자율성 L1–L5는 Feng, McDonald & Zhang (2025) "Levels of Autonomy for AI Agents" 기준 (1편 5절).
> **자율성은 서비스가 아니라 "행동"에 붙습니다.** 같은 쿠팡이라도 주문 내역 조회는 L4, 장바구니 담기는 L3, 결제는 L1.

### 유형별 화면 설계

**A. 모아 보기 → "오늘의 브리핑" 한 화면**
- 메일 브리핑과 같은 화면에 섞어서: "📺 넷플릭스 찜한 시리즈 새 시즌 · 📖 웹툰 3편 새 회차 · 🧑‍🤝‍🧑 밴드 공지 1건(내 답 필요)".
- 서비스별 알림을 **하나로 합쳐** 앱 여러 개를 열 필요를 없애는 것이 핵심 가치 (1편 Mark 2016: 배치 처리).
- "내 답 필요"만 위로 올리고 나머지는 접어 둠.

**B. 비교·구매 → 비교표 + 고정된 장바구니 승인**
```
[계획] 생수 2L×12 · 예산 1만원 · 로켓배송 우선        [조건 수정]
[비교] 3개 후보 (단위가격 · 배송 · 평점 · 광고여부)    ← 위치 편향 방지 (WWW 2026)
        ✓ 추천: A (100ml당 36원, 내일 도착) — 이유 2줄
[장바구니 승인 카드]
   상품 A × 1 · 옵션 2L×12 · 8,900원 · 판매자 쿠팡
   ⚠ 사전 체크된 항목 없음 / 정기배송 아님 / 추가 요금 없음   ← 다크패턴 점검 결과
   [결제 화면으로] [수정] [취소]
[결제] 결제 비밀번호는 사용자 입력 (handoff_payment)
[확인] 주문내역을 다시 읽어 "주문 완료 · 내일 도착" 확인   ← 실행 후 검증 (CHI 2026)
```

**C. 예약·예매 → 선택지 카드 + 취소 조건 명시**
- 결과를 **3개 안팎의 선택지 카드**로 (시간·좌석·가격·취소 수수료). 사용자는 탭 한 번으로 고름.
- 승인 카드에 **취소 가능 기한과 수수료**를 항상 표시 — 예약은 "되돌리기"가 공짜가 아님.
- 매진·대기열이면 **반복 조회로 뚫지 않고** "취소표 알림을 걸어 둘까요?" (E 유형으로 전환). 이유는 5절(법규) 참고.

**D. 나 대신 말하기 → 초안 편집기 + "누가 보게 되나"**
- 승인 카드에 **공개 범위**(전체 공개 / 친구 / 카페 회원 / 채용 담당자 1명)를 크게 표시.
- 초안은 사용자가 직접 고칠 수 있는 편집 상태로 보여 주고, **그대로 승인 비율**을 측정해 말투 학습 품질 지표로 사용.
- 게시 후 **삭제·수정 링크**를 결과 카드에 남김.

**E. 지켜보기 → 조건 알림 + 행동으로 연결**
- "송파구 전세 3억 이하 신규 매물", "SRT 금요일 18시 취소표", "이 상품 1만원 이하" 같은 **조건을 저장**.
- 알림은 조건이 맞을 때만, 알림 카드에서 바로 B/C 흐름 시작.
- 확인 주기는 서비스 약관과 서버 부하를 존중하는 **느린 주기**(예: 30분 이상)로.

**F. 사람 전용 구간 → "여기까지 해 뒀어요" 넘겨주기**
- 본인인증·결제 비밀번호: 지금처럼 보이는 브라우저로 넘기되, **무엇을 입력해야 하는지 한 줄 안내** + 끝나면 에이전트가 이어받음.
- 앱 전용 서비스(배달의민족·카카오 T 등): 비교·결정은 에이전트가 하고, 마지막에 **"배민에서 ○○ 가게 열기"** 처럼 앱으로 넘겨주기(앱이 공개한 링크가 있을 때). 주문 자체는 사용자가.
- 금융·송금·신분증은 **지원하지 않음을 분명히** 말하고 대안(조회용 정보 정리 등)만 제시.

## 6. 이 앱 코드에 바로 적용할 점 (코드를 읽고 찾은 것)

1. **승인이 내용에 묶여 있지 않음** — `lib/agent/safety.dart`의 `grant()`는 요약 문자열을 저장하지만 `consumeGrant()`는 확인하지 않아, 승인 후 10분 안에는 **어떤 민감 버튼이든 1회** 누를 수 있습니다.
   → AP2식으로: 승인 시 금액·상품·받는 사람을 구조화해 저장하고, 결제 직전 화면에서 다시 읽은 값과 **일치할 때만** 통과. 다르면 다시 승인.
2. **앱과 서버의 민감 버튼 목록이 다름** — 서버(`server/app/safety.py`)에는 `예약 확정 · 예매하기 · 탈퇴 · 계정 삭제`가 있는데 앱(`safety.dart`)에는 없습니다.
   둘 다 **게시·등록·올리기·댓글·지원하기·제출·구독 해지·삭제**가 빠져 있어 D 유형(SNS·채용) 보호가 약합니다.
   → 목록을 `services.json`처럼 **한 파일로 공유**하고, 행동 유형별로 나누기.
3. **행동 유형 필드 추가** — `services.json`에 서비스별 `actions`(예: `{"read":"auto","cart":"confirm","pay":"handoff","post":"confirm"}`)를 두면 4절 자율성 설정과 3절 유형별 화면을 데이터로 구동할 수 있습니다.
4. **실행 후 검증 단계** — `finish` 전에 주문내역·예약내역·게시글을 다시 읽어 결과를 확인하도록 프롬프트와 결과 카드에 반영.
5. **민감 정보 입력 멈춤** — 지금은 비밀번호·카드 칸만 막습니다. PrivWeb처럼 **주민번호·계좌·건강 정보** 칸은 알림이 아니라 멈춤으로.
